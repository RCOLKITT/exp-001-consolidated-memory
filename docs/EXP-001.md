## 0. Thesis

> A verifier that accumulates codebase-specific memory of prior defects localizes more subsequent defects in that same codebase than an identical verifier without memory, **without a meaningful increase in false positives** — and every belief it acquired is traceable to the evidence that produced it.

Two claims, tested separately:

- **Efficacy** (Phases 3–4): does memory improve localization?
- **Mechanism** (Phase 1): is the memory correct, replayable, and causally ordered?

Mechanism can pass while efficacy fails. That outcome is still a result and still publishable — it is not a failure of the project.

## 1. Non-goals

- No patch generation. Localization only. Competing with frontier labs on code generation is explicitly out of scope.
- No weight-level learning. No fine-tuning, LoRA, or preference optimization.
- No cross-repository memory. The claim is codebase-specific accumulation.
- No adaptive gate thresholds. Constants, hand-set. The meta-loop is a later experiment.
- No rule compilation. Promoted memories remain retrievable facts.
- No customer, no production deployment, no private data.

## 2. Architecture split

Three seams separate the general kernel from the domain adapter. Everything not listed here is kernel and ships once.

| Seam | Interface | Code adapter implementation |
|---|---|---|
| Outcome oracle | `label(action_id) → good \| bad \| unknown` | Flagged location vs. ground-truth patch location |
| Similarity | `sim(candidate, memory) → [0,1]` | Embedding cosine over defect-pattern text |
| Promotion policy | Config: thresholds, eligible labels, SoD rules | See §6 |

**Kernel components:** episodic buffer with TTL, surprise gate, promotion gate, content-addressed versioned memory store, causal-ordering tokens (vector clocks), version pinning, replay determinism, outcome ledger.

## PHASE 0 — Baseline reproduction
**Duration:** 4 days · **Depends on:** nothing

**Work**
1. Stand up SWE-bench-Live locally with per-task Docker images.
2. Apply the freshness gate: every task must postdate the training cutoff of every model evaluated. Enforce mechanically at import. Record per-task dates for release.
3. Enable time-machine dependency pinning — no package versions later than the base commit timestamp.
4. Run the control-arm verifier (no memory) and reproduce a published localization rate.
5. Evaluate ChainSWE: are its per-repository chains long enough to give memory something to accumulate? If yes, prefer it as the primary corpus.

**GATE 0 — proceed only if all true**
- [ ] Control-arm localization rate lands within a defensible margin of a published baseline
- [ ] Freshness gate enforced in code, not by convention
- [ ] Harness reruns produce identical results on identical inputs

**Kill condition:** cannot reproduce a published baseline. Stop. Every downstream number would be uninterpretable, and this is the cheapest possible place to find out.

## PHASE 1 — Kernel on synthetic streams
**Duration:** 2 weeks · **Depends on:** nothing (runs parallel to Phase 0)

Domain-free. No corpus, no model, no labels. Event streams generated with known properties.

**Work**
1. Buffer with TTL; forgetting is default.
2. Surprise gate: `surprise = 1 - max_similarity(candidate, memory)`; write if `> Θ_surprise` (start 0.35).
3. Promotion gate (§6) running on schedule, not continuously.
4. Content-addressed immutable memory objects with provenance, effective dating, supersession. No in-place edits.
5. Vector-clock causal tokens on every record; wall clock recorded but never used for ordering.
6. Version pinning and replay.
7. Outcome ledger — built here, not later.

**Mechanism assertions (each a test)**
- Surprise gate discards the injected redundant fraction within tolerance
- Promotion fires exactly at threshold, never earlier
- TTL removes unpromoted entries
- Same input hash + same memory version → identical output, every time
- Under simulated clock skew, wall-clock ordering yields a provably wrong answer about what an agent knew; causal ordering yields the correct one
- Supersession creates a new object; no mutation, no reconsolidation

**GATE 1 — proceed only if all true**
- [ ] All mechanism assertions pass
- [ ] The clock-skew demonstration is reproducible and written up

**Kill condition:** replay determinism or causal ordering cannot be made to hold. Stop — the governance claim is the durable contribution and it dies here if this does.

**Note:** the clock-skew artifact is publishable on its own, independent of Phases 3–4.

## PHASE 2 — Corpus and adapter
**Duration:** 1 week · **Depends on:** Gates 0 and 1

**Work**
1. **Pre-register** (§7) — repos, thresholds, kill numbers, split points. Publish before running anything.
2. Build per-repo time-ordered chains. Split by time: positions 1..N build memory, N+1.. evaluate. Never random.
3. Designate one repo as negative control — receives no memory-building runs.
4. Implement the outcome oracle: programmatic match of flagged locations against ground-truth patch locations. No human reading of findings.
5. Wire the three seams to the kernel.

**GATE 2 — proceed only if all true**
- [ ] Pre-registration published and timestamped
- [ ] Per-repo chains long enough that the build split has ≥ the minimum instances required by the power calculation
- [ ] Oracle agreement with manual labels ≥ 95% on a 50-instance hand-check

**Kill condition:** oracle is too noisy to trust, or chains are too short. Stop, or reduce to fewer repos with longer chains.

---

## PHASE 3 — Learning phase
**Duration:** 1 week · **Depends on:** Gate 2

**Work**
1. Run build-split chains through the treatment pipeline in chronological order.
2. Populate buffer, run nightly promotion.
3. Freeze. Pin the memory version. No promotion after this point.

**GATE 3 — the early kill, and the most likely one**
- [ ] Surprise gate discards **>60%** of candidate writes as redundant
- [ ] At least a usable count of memories promoted per repo (set the floor during pre-registration)
- [ ] Promoted memories are human-legible on inspection — a sample reads as real defect patterns, not noise

**Kill condition:** discard rate below 60%. Either retrieval is too weak to recognize what memory already holds, or defects in this corpus don't repeat. Either way there is nothing to consolidate. Stop and diagnose rather than proceeding to a foregone null result.

---

## PHASE 4 — Evaluation
**Duration:** 1 week · **Depends on:** Gate 3

**Arms**

| Arm | Config |
|---|---|
| Control | No memory retrieval. `memory_version = null`. |
| Treatment | Memory retrieval on, version pinned to the frozen snapshot. |

Same model, prompt scaffold, temperature, seeds. Memory retrieval is the only delta. Interleave arms; randomize instance order within arm.

**Metrics — always reported as a pair**

| Metric | Definition |
|---|---|
| Localization rate | Defects whose location was correctly flagged / defects present |
| False-positive rate | Flags with no ground-truth match / total flags |

Secondary, non-gating: retrieval hit rate, promoted memories never retrieved, median time-to-verdict, per-repo breakdown.

**GATE 4 — the result**
- [ ] Localization lift ≥ **15 points absolute** (raise to match minimum detectable effect if power says so — never lower after seeing data)
- [ ] False-positive rate rise ≤ **5 points absolute**
- [ ] Effect present in a majority of repos, not driven by one
- [ ] Negative-control repo shows no lift

**Fail:** anything else, including a lift that only survives by inflating false positives, and including a lift that also appears in the negative control.

## 6. Promotion policy (adapter config)

Promotion requires **all**:

1. `occurrence_count >= 3` distinct source records
2. `distinct_input_hashes >= 3` — pattern generalizes beyond one artifact
3. No unresolved contradiction with an existing promoted memory
4. Separation of duties — the proposing agent is not the approving agent
5. **Only `label = bad` confirmed defects are promotion-eligible.** Self-poisoning guard: a verifier that can learn from its own false positives will confidently teach itself to be wrong, and that failure looks like success from the inside.

## 8. Threats to validity

| Threat | Mitigation |
|---|---|
| **Contamination** — model memorized the fix | Freshness gate; ~20pp gaps observed between contaminated and temporally-filtered evaluation |
| Dependency drift breaking old tasks | Time-machine version pinning to base commit timestamp |
| Temporal leakage across the split | Chronological split only; never random |
| Threshold shift disguised as learning | Paired metric; false-positive ceiling |
| Repo cherry-picking | Pre-registered repo list; per-repo reporting |
| Effect is generic, not codebase-specific | Negative-control repo |
| Self-poisoning | Only confirmed defects promotion-eligible |
| Model drift across the window | Interleaved arms; pinned model version |
| Confirmation bias in matching | Programmatic oracle; no human reading of findings |
